# Deploying Excel Connect Hub

Everything runs on **Render**, from one file: `render.yaml` at the repository
root. One Blueprint apply creates all three pieces.

| Piece | Root dir | Service |
| --- | --- | --- |
| Express API | `backend` | `excel-connect-hub-api` |
| Next.js frontend | `frontend` | `excel-connect-hub-web` |
| Postgres | — | `excel-connect-hub-db` |

Both are **Web Services**, not Static Sites. The frontend is not a static
export — it has server components, and `next start` has to run. If a Render form
ever asks you for a "Publish directory", you are in the wrong form.

---

## The one-step path

1. <https://dashboard.render.com> → **New +** → **Blueprint**
2. Pick `Exaudlaizer/Excel-connect-hub`, branch `feature/platform-overhaul`
3. Render reads `render.yaml` and lists two services and one database
4. **Apply** — there is nothing to fill in

Email is intentionally not configured, so verification codes print to the
service log and every flow still works. Add the `SMTP_*` keys in the dashboard
later to send real mail.

A manually created Web Service **ignores this file**. `render.yaml` only applies
to services created through New + → Blueprint.

Everything else is already in the file: `DATABASE_URL` is wired to the database,
`JWT_SECRET` is generated by Render, and the two services point at each other.

### Then create the tables

API service → **Shell** tab:

```
npm run db:migrate
npm run seed:admin -- --email=you@example.com --password=YourStrongPassword --name="Site Admin"
```

Without this every login fails with `relation "users" does not exist`.
`db:migrate` only adds what is missing, so it is safe to re-run after a schema
change.

### Then check it

- `https://excel-connect-hub-api.onrender.com/health` → `{"status":"ok",…}`
- `https://excel-connect-hub-web.onrender.com` → the app

If Render assigned different hostnames (it appends a suffix when a name is
taken), fix `CLIENT_ORIGIN` on the API and `NEXT_PUBLIC_API_URL` on the
frontend to match. See the rebuild note below.

## Setting it up by hand instead

If you are filling in the forms yourself rather than using the Blueprint:

**API** — New + → **Web Service**

| Field | Value |
| --- | --- |
| Root Directory | `backend` |
| Build Command | `npm ci` |
| Start Command | `npm start` |
| Health Check Path | `/health` |

**Frontend** — New + → **Web Service**

| Field | Value |
| --- | --- |
| Root Directory | `frontend` |
| Build Command | `npm ci && npm run build` |
| Start Command | `npm start` |

Do **not** add a `PORT` variable. Render assigns the port and passing your own
breaks its port detection.

**Database** — New + → **Postgres**, free plan. Then copy its **Internal
Database URL** into the API's `DATABASE_URL`.

**Minimum environment variables on the API:**

| Key | Value |
| --- | --- |
| `DATABASE_URL` | the Internal Database URL |
| `JWT_SECRET` | use Render's **Generate** button (32+ chars) |
| `CLIENT_ORIGIN` | the frontend's URL, exactly |
| `TRUST_PROXY` | `1` |

`NODE_ENV=production` is set by Render already. `JWT_EXPIRES_IN` defaults to
`7d` in code. Leave the `SMTP_*` keys unset.

**On the frontend:** `NEXT_PUBLIC_API_URL` = `https://<api-host>/api` — the
`/api` suffix matters, every route is mounted under it.

## Things that will catch you

**`NEXT_PUBLIC_*` is baked in at build time.** It is compiled into the browser
bundle, not read when the server starts. Changing it needs **Manual Deploy →
Clear build cache & deploy**, not a restart.

**Free services spin down after ~15 minutes idle.** The first request then takes
up to a minute on each service. Nothing is broken; it is waking up. Open the
API's `/health` in another tab before demoing to someone.

**Uploads do not survive a redeploy.** The free plan has no persistent disk, and
`uploadController` writes to `backend/uploads/`. Files last as long as the
instance does. For permanent uploads set `plan: starter` on the API service in
`render.yaml` and uncomment its `disk:` block.

## Reading a failed deploy

The API connects to Postgres before anything else, so the first error is nearly
always the database.

| Log line | Cause |
| --- | --- |
| `Invalid configuration: … JWT_SECRET …` | `JWT_SECRET` unset, under 32 chars, or still the placeholder |
| `Invalid configuration: … DATABASE_URL …` | `DATABASE_URL` unset |
| `SequelizeConnectionRefusedError: connect ECONNREFUSED …` | Nothing listening at that address; check the URL is the Internal one |
| `getaddrinfo ENOTFOUND …` | Wrong or truncated host |
| `password authentication failed` | Partial paste of the connection string |
| `Cannot find module '…/server.js'` | Root Directory is not `backend` |
| `npm error … ENOENT … package.json` | Root Directory is not set |
| `No open ports detected` | The app crashed before listening — read the lines above it |

A healthy API start looks like:

```
PostgreSQL connected
Rate limiting: in-process store (set REDIS_URL to share counters across instances).
Mail: no SMTP configured — messages will be printed to this console.
Excel Connect Hub API running on port 10000
```

All three of those middle lines are normal.

## Running locally (unchanged)

```powershell
cd backend;  npm run dev     # terminal 1
cd frontend; npm run dev     # terminal 2
```

Your local `.env` and `.env.local` are never read by Render, and nothing here
modifies them.
